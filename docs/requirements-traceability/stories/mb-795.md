# MB-795 - Consultation schedulers continue past inconsistent appointment rows

## Scope (2026-11-05)

The 2026-11-03 staging hotfix (backend PR #254, promotion #255) isolated each
scheduled video end and room closure and let a reopened active video appointment
restore `SESSION_ENDED` from its existing `video-ended:<id>` history. This
follow-up closes the named hotfix follow-ups:

- MB-795-HISTORY: under the existing pessimistic appointment lock, a prior
  `video-ended:<id>` row is reused only when it records `CONFIRMED` or
  `IN_PROGRESS` to `SESSION_ENDED` with reason `SCHEDULED_WINDOW_ENDED` or
  `SPECIALIST_VIDEO_END_CONFIRMED`. Any other row is an incompatible audit fact:
  the item fails in its own transaction, stays in its current state and the
  scheduler continues with later items. History is never inserted, updated or
  deleted for that appointment.
- MB-795-REGRESSION: disposable PostgreSQL tests cover compatible replay
  (original history row, outbox count, HELD credit, ledger and earning unchanged;
  repeat is a no-op), concurrent end callers for fresh and reopened sessions
  (one transition, one history row, one outbox event only for the genuine
  transition), incompatible history isolation, not-due and unconfirmed
  appointments, and invalid-credit expiry (period/account mismatch, non-held
  credit and wrong hold) rolling back appointment, credit, history and outbox
  while a later valid request expires. A unit test proves a failed end item and a
  failed closure item do not starve later items or the other loop.
- Scheduler failure logs contain only the operation, appointment ID and the
  error code (API errors) or exception class, never exception messages, provider
  payloads or account data.

A restored session keeps the 2026-11-03 owner ruling: no second appointment
status outbox event, because the original end already published it. Timer end
never completes the appointment, consumes or releases its HELD credit, or
creates an earning. Invalid-credit expiry remains fail-closed; a permissive
status-only expiry would need a separate approved policy change. No REST, event
or persisted-shape change and no migration.

## Operator audit (read-only)

Run against the Consultation database with a read-only role. Both queries are
bounded and change nothing.

Due REQUESTED rows that expiry cannot release:

```sql
select * from (
  select a.id, a.decision_deadline_at, a.user_account_id, a.service_credit_id, c.state, c.appointment_id,
         p.account_id as period_account,
         case when c.id is null then 'CREDIT_MISSING'
              when p.account_id <> a.user_account_id then 'PERIOD_ACCOUNT_MISMATCH'
              when c.state <> 'HELD' then 'CREDIT_NOT_HELD'
              when c.appointment_id is distinct from a.id then 'CREDIT_HELD_FOR_OTHER_APPOINTMENT'
              else 'CONSISTENT' end as anomaly
  from appointment a
  left join service_credit c on c.id = a.service_credit_id
  left join service_credit_period p on p.id = c.period_id
  where a.status = 'REQUESTED' and a.decision_deadline_at <= now()
) due
where anomaly <> 'CONSISTENT'
order by decision_deadline_at, id
limit 100;
```

Due active video rows whose prior end history is incompatible:

```sql
select a.id, a.status, h.from_status, h.to_status, h.reason, h.changed_at
from appointment a
join appointment_status_history h on h.appointment_id = a.id and h.idempotency_key = 'video-ended:' || a.id
where a.modality = 'IN_APP_VIDEO' and a.status in ('CONFIRMED', 'IN_PROGRESS') and a.scheduled_end_at <= now()
  and (h.from_status in ('CONFIRMED', 'IN_PROGRESS') and h.to_status = 'SESSION_ENDED'
       and h.reason in ('SCHEDULED_WINDOW_ENDED', 'SPECIALIST_VIDEO_END_CONFIRMED')) is not true
order by a.scheduled_end_at, a.id
limit 100;
```

Any row returned needs a concrete, separately authorized repair agreed by the
owner and a Consultation maintainer after provenance review. Never provision
substitute credits, relink credit owners, delete or rewrite history, or create
RELEASED/CONSUMED facts to silence the error. Anomalies that stay due are
retried every expiry tick and logged each time, but cannot starve valid requests:
the scheduler pages through all due requests by id in 100-row batches
(MB-795-BATCH, 2026-11-06). Both queries above are executed against seeded
anomalies in `AppointmentDecisionIntegrationTests` and
`VideoAccessIntegrationTests`, so a schema change that breaks them fails the
build (MB-795-AUDIT-SQL).

credit's own account, one `appointment-expiry:<id>` history row, no outbox

`6c132487-d9a2-4a6d-a58d-589acb561866` reached `SESSION_ENDED` on normal ticks

story performs no shared-data change.
