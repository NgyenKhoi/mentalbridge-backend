# MB-813 - Classify definite PayOS payout submission failures

## Backend scope (2026-11-05)

This correction follows [ADR 0047's runtime clarification](../../adr/0047-payos-active-gateway-momo-dormant.md#mb-813-payout-rejection-runtime-clarification-2026-11-05)
and relates to MB-787 bank payout and MB-788 funded staging interoperability.
PayOS rejected an initial 2,625 VND payout with HTTP 403 because the server IP
was not allowed. The adapter treated the rejection as UNKNOWN; later empty
reference lookups could not establish a terminal result, leaving earnings
PROCESSING and the existing FAILED-only admin retry unavailable.

Initial create HTTP 401/403 now maps to
`FAILED / PAYOUT_PROVIDER_ACCESS_DENIED / COMPLETE`. The existing locked terminal
transition returns reserved earnings to AVAILABLE with original item ownership,
history and minimized provider observation evidence. The existing ADMIN retry
retains frozen provider/destination/amount/lineage and revalidates every gate.
One persisted attempt has one submit; SDK/HTTP retries and redirects remain
disabled, and specialist/admin command replay never resubmits that attempt.

Empty reference lists and query authentication failures preserve uncertainty.
The [official PayOS API](https://payos.vn/docs/api/) specifies no bounded
list-visibility guarantee, so no grace window authorizes automatic failure.
UNKNOWN/NEEDS_REVIEW retains reserved funds at the existing 24-hour horizon.
No admin action may release uncertain funds based only on absence from a list;
this story introduces no manual resolution endpoint or new financial authority.

Provider diagnostics contain operation, payout/attempt UUIDs, HTTP status and
a bounded sanitized provider code only. The pinned SDK's
[APIException](https://raw.githubusercontent.com/payOSHQ/payos-lib-java/v2.0.1/src/main/java/vn/payos/exception/APIException.java)
retains status/code, while exception messages can contain raw provider data
and must not be logged. Existing OpenAPI `failureCode` strings accept the safe
new code without schema, generated-consumer or web changes. No migration is
required; the deployment target is consultation only.
